# 侧边会话做深调研

> 2026-10-09 的调研记录。现在怎么运作、采用了哪些结论，以 [design.md](design.md) 为准；当时的代码核对、分批和验收草案、交接说明、给契约的补充建议已经删去，在 git 里能找到。
> 依据：总体计划（当时的 `docs/PLAN.md`）、[已确认设计](design.md)、[学习流程](../journey.md)、[契约](../contracts.md)，以及下文的一手研究、开源实现和本机锁定版 DSH 类型。批注的选择、锚定和学习科学依据见[annotation 调研](../annotation/research.md)。
> 范围：隔离答疑、上下文、帮助记账、总结、测试边界和修改提案。

推荐先保证：**给过的帮助及时、准确地记账；侧边会话按真实权限答疑；结束会话后总结和笔记可恢复且不重复。** 再做针对性反馈、误解检查和提案。回答顺畅、学习者满意、总结完整，都不能代替撤掉帮助后的独立作答证据。

## 1. 结论与推荐取舍

| 问题 | 推荐项 | 不采用的做法及原因 |
|---|---|---|
| 角色 | 同一学习产品的隔离答疑窗口，复用资料与知识服务 | 另建一套主老师、课程调度或长期记忆系统：增加多份状态和竞争修改 |
| 教学方式 | 先了解具体卡点，给刚好够用的提示；普通学习中允许主动要求完整讲解 | 固定每轮只反问、永不讲答案：未必适合新手，也违背已确认可请求完整帮助的方向 |
| 测试期间 | 按 assess 的实际测试状态限制为操作说明；深入讨论先明确离开独立测试并记帮助 | 只写“不要泄题”提示：不能阻止工具泄露、旧会话绕过或模型直接解题 |
| 工具 | 两个资料只读工具，调用时核对会话、课程及测试策略 | 直接复用主老师的整套 library/tools：其中已有资料写入工具 |
| 上下文 | 保存提问时的对象和版本；每轮刷新最小政策与必要状态；需要更多内容再取 | 全图、全会话、完整主老师简报常驻：成本高，且可能带入测试设计或无关内容 |
| 帮助记录 | 在实际给帮助的回复上关联发生时间、对象和会话事件；失败可补账 | 等关闭会话再用总结生成时间记账：聊天后立即作答会被漏判 |
| 总结 | 每个结论和误解候选有原消息依据；分开学习者观点、助手说法和原文支持 | 一份流畅的无出处摘要直接变成确定的误解和知识事实 |
| 关闭与恢复 | 持久化关闭流程、固定会话截点，逐步发布并可重试 | 仅靠内存 busy、一次函数调用和数据库 UNIQUE：不能覆盖跨文件、会话与事件的失败窗口 |
| 提案 | 侧边会话生成草稿，学习者点击提交；core 保存，tutor 评估，主人单元执行 | 模型根据聊天直接修改课程、教材、题库或图谱 |
| 误解检查 | 记录可检验假设；由 tutor/planner 经 assess 的练习题池安排检查 | 在聊天里另造题库；把会话评价当作独立测验 |
| 评价 | 分开工程正确性、教学回复质量和真人学习效果 | 用模拟学生、自动裁判或聊天满意度证明保持与迁移 |

表中的设计推荐不是已确认决定。测试独立性、证据只追加、修改走主老师和单元归属仍按既有设计执行。

## 3. 真人研究能支持什么

### 自由给答案与受约束辅导的结果不同

Bastani 等在近千名土耳其高中数学学习者中比较普通 GPT-4 帮助与有教学约束的 tutor。普通帮助提高有工具练习表现，但撤去工具后的考试表现下降；受约束 tutor 没有出现这一明显下降，独立考试相对对照的提升并不显著。其约束包含教师提供的解答和错误资料，不能归因于一句“苏格拉底式教学”。[Generative AI without guardrails can harm learning，作者全文](https://hamsabastani.github.io/education_llm.pdf)

**应用建议：** 让完整帮助有明确标签、发生记录和下一次撤掉帮助的验证。不要把受帮助后的成功写成独立成功，也不要禁止一切讲解。研究不是本项目中文化工原理的效应预测。

### 正面结果依赖任务与平台设计

Kestin 等 2025 年研究纳入 194 名大学物理学生，两个课题采用交叉随机设计；研究型 AI tutor 的即时测验表现优于课堂主动学习。平台逐部分推进活动，使用准备好的解题内容，作者明确指出单靠系统提示不能稳定维持多步骤顺序。该实验没有证明所有通用聊天或长期保持都有同样收益。[AI tutoring outperforms in-class active learning](https://www.nature.com/articles/s41598-025-97652-6)

**应用建议：** 本产品已确认的出处、任务和作答环节比拟人措辞更关键。聊天围绕用户卡点提供可追溯帮助，独立验证仍回 assess；不把论文效应量移植成产品验收阈值。

Pardos 与 Bhandari 2024 年在 274 名参与者、四类数学题中比较生成提示、人工提示和无提示。生成与人工提示组的增益没有显著差异；投入实验的提示经过检查，初始生成在约 32% 的题目上未通过质量检查。不能把“没有显著差异”直接解释为任意实时模型输出都统计等效。[ChatGPT-generated help…](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0304013)

**应用建议：** 检查公式、条件、单位、步骤和出处支持；模型自评不替代核对。遇到资料缺口，应明确说明，不能靠一般知识补成有出处的解释。

### 2026 年新结果仍需限定解释

StudentBench 2026-09 的预印本报告 2383 名英语成人参与者，在一小时 GRE 辅导后的无帮助测试中，合并 AI 组与真人辅导组通过其设定的等效检验。研究仅测即时增益，没有长期保持或中文理工验证；对照也未单独隔离“只练习题”的收益。它提供了真人评价方法，不能作为本项目模型选型结论。[StudentBench v1](https://arxiv.org/html/2609.28470v1)

**应用建议：** 将辅导质量、延迟、费用、投入程度与无帮助学习增益分开报告。响应速度与学习结果的相关关系不应当成“更快必然学得更好”的因果证据。

### 会求助与学会知识也要分别测量

Roll 等 2011 年的 Help Tutor 研究用几何 tutor 的元认知反馈改善求助行为，减少直接跳到底部答案提示等现象；论文也报告相应研究期间没有观察到学科知识增益的优势，讨论额外认知负担等可能原因。第二项研究包含求助指导和自我评估，不能把效果归于一种弹窗或强制等待。[Improving students’ help-seeking skills](https://pact.cs.cmu.edu/pubs/Roll,%20Aleven,%20McLaren%20&%20Koedinger%202011.pdf)

**应用建议：** 普通学习时可以邀请用户说“我卡在哪一步、试过什么”，但不把填写这些信息当作获得帮助的硬门槛。用户不知道卡点时直接协助定位。不要按问得少、提示点击少或回答看得久来奖惩；这些行为改变不证明知识学会，也不能证明读过提示。

自我解释的正面、无显著差异及近/远迁移证据统一见[annotation 调研](../annotation/research.md#更贴近数字学习的证据以及反例)。它们要求按具体推理设计反馈，不能仅给侧边角色加一句“多使用苏格拉底式提问”就宣称完成教学设计。

### 推荐的教学动作按情境选择

| 用户情境 | 首个可用动作 | 何时加深及怎样验证 |
|---|---|---|
| 问一个定义或资料位置 | 给出处和直接的简短说明 | 不强迫先猜定义；需要学习验证时安排检索或应用 |
| 有步骤，但卡在某次推导 | 确认该步骤、点出相关条件，提供一个可执行提示 | 用户仍无进展时讲解该步；帮助日志关联本步和对象 |
| 自我解释漏掉条件 | 指出缺少的条件，邀请说明改变条件后是否仍成立 | 接受其他正确表达；查不清原文时保留未知 |
| 没有背景、完全不知道从何开始 | 给小范围的完整示范或拆清起点 | 不连续反问；随后换一个无帮助任务验证 |
| 主动要求完整解答 | 普通学习允许展示，明确帮助性质 | 记录完整解答/答案暴露，后续独立题避免复用同题 |
| 质疑教材或老师解释 | 对照原文、条件和实际反例 | 区分内容错误与理解问题；必要时走提案 |
| 测试期间 | 确定性的操作说明 | 讨论题意前完成退出独立测试的转换 |

四档帮助描述实际内容，不是固定的每轮升级阶梯。完整推导与只给数值答案都能破坏同题的独立性；讲解新知识与当前题的提示也需分别关联。没有证据支持“每问两轮自动升一级”或“困难学习者永远从最小提示开始”，不设这种伪适应规则。

### OATutor 的提示不是只在结束时记账

**应用建议：** 借“帮助展示处有对象关联”的作用链，复用 DSH 的持久消息身份。其 BKT 更新、帮助惩罚模式及客户端状态不是本产品的规则；不引入问问题扣分或强制按依赖读完提示的行为。开源实现提供参考，不证明它的所有日志、流式取消或学习结果都已可靠。

## 5. 只读权限与测试独立性

### 权限按可执行动作约束

侧边预设不能挂主老师的资料工具全集。推荐 library 工具提供可核对的能力选择，只给 search_library 和 read_section；缺资料时返回缺口，学习者可交回主老师补资料。让 sidechat 自己联网并入库会改变已确认范围，不能因为 search_web 是“读”就顺带开放 add_web_sources。

策略应绑定可信的会话角色和归属，不接受模型自行声明 actor 或 courseId 就放行。每次工具调用验证目标课程、材料范围与当前测试政策。客户端隐藏按钮、预设文案和工具说明都不等同于服务端边界；已打开的旧会话也要接受新政策。

当前 add_web_sources 调用 library.addWeb 并将 actor 写为 teacher；这是可执行写入路径的静态证据，本次没有尝试调用或复现写入。

补充追踪 [kit/index.ts](../../packages/kit/src/index.ts)：textTool 负责工具定义、文字返回和 LaTeX 修复；linkOf 从实际 agent.session 取 core 的会话归属，能避免模型随意伪造课程，但只检查存在 courseId，没有验证 teacher/side-chat 角色或测试政策。因此推荐保留可信会话定位，再补动作政策，不能把已有 linkOf 误说成已经实现只读授权。

### 只读资料也能泄露答案

search_library 的类型参数包含习题和答案，read_section 可读取包含解答的整节。限制必须作用于实际返回内容，包括答案片段、同页区域、章节整读和预留题相关材料。不能仅删除“答案”标签，保留正文或图片中的完整解答。

assess 是测试政策与题池主人。sidechat 和 library 通过契约取得当前活动测试、题目与允许帮助范围；测试预留题及其答案不能作为普通教学上下文或检索结果暴露。不要复制一套“根据页面标题猜测试”的判断。

### 测试期间采用明确的模式边界

[assess 的测试独立性设计](../assess/design.md)已经确认：独立测试中的侧边会话只处理操作说明；深入讨论需离开测试，这次作答记为受帮助。建议如下：

| 情境 | 可提供内容 | 记录与转换 |
|---|---|---|
| 普通阅读、自我解释和练习 | 原文支持的提示、讲解；用户明确要求可完整展示 | 按实际帮助记账，随后独立验证由 assess 安排 |
| 独立测试进行中 | 交卷、计时、照片确认、题目显示等操作说明 | 操作说明本身不记概念帮助；不提供知识检索与解题上下文 |
| 学习者请求讨论当前测试题 | 先说明离开独立测试的结果，完成明确转换后讨论 | 保留原测试条件及发生记录，由 assess 处理该题的受帮助属性，不重写原独立条件 |
| 测试完成后的复盘 | 按 assess 提供的可复盘范围解释 | 若仍属预留题，后续可用性与是否已看答案由 assess 记账 |

要检查“先开侧边会话再开始测试”“切页后继续旧会话”“粘贴题干要求直接解答”等情况。仅移除检索工具，模型仍可用内在知识解题；若产品要承诺严格的操作帮助，可直接提供确定性的操作说明，测试期间不让自由对话模型接收题干。模型提示只能作为行为约束，不能宣称有绝对防泄露保证。

## 6. 上下文与模型交互

### 提问快照与动态政策分开

打开时保存用户真正选中的内容、对象、课程和当时版本。后续正文修订不能悄悄把问题换成新版内容；可显示“这里已修订”，让用户选择继续讨论原版或切到新版。批注定位失败时传原引文及定位状态，而不是猜一处新位置。

每轮开始核对当前测试模式、会话是否可继续，以及所需节点的最新学习状态。摘要以局部证据解释“独立完成过”“有帮助完成”“待验证”“有疑点”；不把全课程规则、全部日志和主老师历史放进侧边上下文。

页面与资料文本是讨论对象，里面出现“忽略规则、修改课程”等文字不应成为角色指令。通过 typed context 标明来源和性质，动作权限仍由服务检查。

### 上下文有预算，也有取更多信息的路

首轮推荐只包含提问快照、相关节点、必要前置关系、局部状态和资料入口；限长要计入标题、出处、标签与元数据。长表、公式和图片不能简单截断到失去条件，超限时保留完整小单元并提供分段读取。

全课程节点名单不是识别知识点的唯一办法。先使用选择对象已有的知识关联，再按会话主题检索候选；无法确定时保留未关联，不强制选最近标题。跨话题需要补候选时可请求主人服务。单元不互相 import 业务实现。

回复遵守 [learning-prompts-tools](../../.agents/skills/learning-prompts-tools/SKILL.md)：先说明当前卡点，给一个可行动的支持，再根据反馈加深；避免连续追问而不提供帮助，避免泛泛表扬、模型自我介绍和内部 ID。引用仍用可定位的资料片段，模型说法本身不是出处。

输入图片复用既有消息图片通道；当前中转不支持工具结果中的图片，不应设计成“读工具返回图片后模型自然看见”。手写内容进入判分前的识别确认由 assess 负责，sidechat 不绕过这个步骤。

### 首轮注入应可恢复

contexted Set 可作为缓存，不能是唯一事实。推荐将快照形成版本与已注入的持久消息/seq 关联；注入成功后再记录完成，失败可以重试。重启后读持久事件识别已注入内容，避免重复塞同一大段或错误跳过。

open 和发送首问作为可恢复的两步流程：请求身份固定，已建会话可重用；创建或选模型失败显示具体原因，不能留下“看起来可聊但 DSH 尚无会话”的记录。发送失败后仍能找回已创建的会话与草稿。

## 7. 帮助、总结和结束恢复

### 帮助发生时间必须早于受帮助的作答

当前逻辑可形成以下顺序：10:00 讲解，10:03 作答，10:10 结束会话；帮助日志默认写 10:10，learner 因其晚于作答而忽略。这是代码推导的待验收场景，没有在真实模型上复现。一直不结束会话或总结失败也可能没有帮助日志。

现有 [NewLogEntry](../../packages/contracts/src/schema/evidence.ts)已支持显式 `at`，help.given 已支持 problemId 和 context 中的 test/lesson/session。应使用实际发生时间及可信关联，不必为了传时间先扩一整套日志格式。

推荐在可见帮助回复形成时记账，并持有到 DSH 消息 seq 的关联。先区分操作说明、问题澄清与实际概念提示，再记录四档帮助；“问了问题”或“打开窗口”不等于得到帮助。概念讲解关联确实涉及的节点，题目帮助还关联对应题目与测试。

**另一项前置依赖是作答时间。** assess.submit/answer 先 await grade，再进入 record；record 内才写 submittedAt 和 attempt.graded 日志。因而即使帮助日志及时，10:03 提交答案、10:04 看讲解、10:05 判分写日志，也可能按现有 learner 的日志时间被判为作答前受帮助。批量判卷时，不同题甚至有不同的判分后时间。此结论来自[assess 源码](../../packages/assess/src/index.ts)顺序分析，未做故障实验。

独立性应比较帮助发生与该答案版本的真实提交/锁定边界，由 assess 在异步判分前保存答案快照和可信服务端时间；判分时间、日志落账时间与帮助归因时间分开。改答案或补交属于新的作答版本，不能复用旧边界。补齐这条链需要 assess/core/learner 的接口设计，本调研不修改它们；sidechat 单独“立即记帮助”仍不能验收整条独立性链。

模型分类若异步完成，要保存待归因的回复；在相关作答形成独立性结论前补齐，或由 learner 显示待核实，不能把分类失败默认为没有帮助。该门控需要 learner 契约配合，sidechat 不能自己写掌握状态。

流式回复取消前可能已经显示答案。只听最终 assistant/message 会漏掉实际暴露；但将所有临时 token 当可靠结论也不合适。需要区分已展示内容、完整回复和待归因帮助，针对取消、断线和刷新设计补账。帮助一经发生不能因删除会话、关闭面板或后续取消而抹除。

还应区分“模型生成了、系统提供了、界面已展开或收到、学习者自报看了”。最终提交只证明内容可被提供，页面事件不证明真正阅读或理解。首批可以采用保守且明确的提供/展示规则，但要写清含义；隐藏面板中尚未显示的回复，不凭生成时间宣称用户已阅读。时间来自可信服务端及对应事件，客户端显示记录作为暴露线索，不让任意客户端时间改写证据。

记录幂等以会话、持久消息身份和帮助项为依据，而非仅靠文本相等。结束时总结已有帮助记录；若发现遗漏，按原发生时间补记并触发重算，不再用总结时间重复追加。通用帮助更正和待归因状态尚无完整契约，应由 core/learner 与生产者共同定义最小扩展，日志仍只追加。

### 总结是可审核的派生结果

推荐从固定、完整的会话消息范围产生总结，条目保留来源消息/seq，至少区分以下几类：

| 条目 | 要核对什么 |
|---|---|
| 学习者问了什么 | 真实学习者消息；不把注入上下文、原文引语或助手追问记成提问 |
| 助手解释了什么 | 原回复与资料引用；未验证支持时标为待核实说法 |
| 学习者自己的结论 | 确实由学习者表达；不把助手建议写成已接受或已掌握 |
| 可能误解 | 对应原句、具体节点和理由；保留否定、引用、假设、已纠正状态 |
| 给过什么帮助 | 以帮助记录和可见消息为依据，带发生时间与对象 |
| 修改建议 | 区分讨论、草稿、用户提交和实际应用；summary 不代替提案状态 |

schema 校验只能检查形状和 ID，不能证明摘要忠实。增加说话人、原句存在性、范围和对象关联的确定性检查；概括的语义忠实度用独立评审。每个误解应有自己的 nodeIds，不能把整段会话涉及的所有节点套给每条误解。

长会话按完成的消息区间分段，缓存区间与摘要版本，最终核对跨段指代、否定和纠正。固定输入范围、内容指纹和模型配置；重试不重新摘要已完成区间。具体长度与费用上限需要合成会话测量，不在调研中虚构 token 或耗时基准。

学习者可以对总结标“这不是我的意思”，追加纠正并保留历史；已有信号更正须走追加日志及 learner 重算。助手提出错误解释时应单独标明内容问题，不反向诊断学习者。

### 锁定版 DSH 可提供的恢复边界

本次读取的是本机 `.tools/dsh/node_modules/@deepseek-ai/*/lib/types`，版本锁定 `0.2.0-rc.2`，未按网上最新 API 猜接口：

| 能力 | 可据此设计什么 | 不能假定什么 |
|---|---|---|
| sessionController.create | 以固定 sessionId 重试创建/接管 | core 归属登记与 DSH 创建已经原子完成 |
| inspect / page | 不激活会话读取持久历史，分页处理完成前缀 | inspect 自动等到正在流式生成的回复完成 |
| follow / session/event | 完整 opening、持久事件及 seq，可观察提交进度 | 启动前的 seed 事件都会重新通过 live hook 广播 |
| assistant-stream | 临时流式展示 | 临时 chunk 就是永久完整回复 |
| cancel | 发出取消请求 | 请求被接受即会话已经静止 |
| session surface projection | 获取替换区间后的有效消息视图 | 所有原始日志事件都仍是当前有效发言 |

因此应以持久序号和有效消息视图确定总结截点。取消后等待真实状态终止或确认完整前缀；不能将 cancel 返回值直接作为“没有回复在继续生成”。运行时适配的异常与替换消息仍需合成 DSH 验证。

### 关闭流程要能跨边界继续

推荐 sidechat 持有关闭任务和进度：认领关闭 → 等待/停止活动回复 → 固定截点 → 整理结果 → 发布笔记 → 提交关联日志与总结 → 完成会话归属关闭 → 发布通知。每一步有稳定业务身份，已完成步骤可读回，不要求一次函数调用包住所有资源。

当前 close 两次并发可能同时通过“无总结”检查，分别生成并追加文件，之后一个 INSERT 被 UNIQUE 拒绝。文件成功但总结事务失败后重试也可能再追加；总结已存而会话关闭或通知失败时，提前返回不会修复后半段。这些是明确的故障注入验收点，不是已发生事故。

课程 Markdown 仍只由 core 写。需要 core 提供按稳定条目身份核对或恢复追加的能力，使同一总结最多一条笔记；不能直接绕过 core 写文件。现有普通 append 没有跨 sidechat 整条操作的幂等保证，但其自身的文件版本提交不应被误说成无保护写盘。

DSH 持久会话是对话真相；sidechat 数据库持有结构化结果、进度和关联；笔记是通过 core 保存的可读总结。不要复制第三份完整会话或建立可各自修改的两套摘要。页面隐藏只收起窗口，“结束并总结”才推进关闭；历史会话及失败整理可被找回。

完成后发 learning/sidechat-summarized，并按既有约定发一次 learning/handoff 的完成通知；主老师是否被唤醒由 tutor/planner 决定，不把全文总结塞入主老师消息，不主动打断课程。通知交付与消费者去重应明确约定，不能声称 emit 自带跨进程恰好一次保证。

### 信号的实际消费者也要验收

| 生产链 | 已有消费链 | 缺口和主人 |
|---|---|---|
| sidechat.close → core.log.append → learning/logged | learner 订阅 logged，按节点重算；curriculum 复盘工具读取帮助、疑问和误解 | 更正、晚到补账和待归因如何改变旧作答，需要 learner/core 规则；不修改 Curriculum |
| sidechat.close → learning/sidechat-summarized | core 转发到页面 feed，sidechat 页面刷新 | 不等于 tutor 已读取或评估；主老师何时读总结仍由 tutor 设计 |
| core.proposals.create → learning/proposal-created | 已有存储和页面推送契约 | 未追到完整 tutor 评估及主人应用链，不能验收端到端修改 |
| learning/handoff → tutor 内存 pending/timer → deliver | 主老师可收到完成通知并按 planner 下一步推进 | pending 不是持久队列；重启窗口、汇总去重和补发由 tutor 负责 |

core.log 的 afterCommit 保证通知安排在提交后，但不是持久投递证明。若日志提交后、状态重算前重启，恢复应能从持久日志继续；不能把“sidechat 已存总结”当作所有消费者都收到。记录条目与消费者进度/水位的归属要明确，避免每个单元各建一套通用事件总线。

## 8. 误解检查与修改提案

### 检查是一个由证据闭合的流程

待核实误解保留具体命题、原句、相关节点及其产生情境。tutor 在合适的课时小结、复盘或阶段设计中读取，由 planner 决定下一步，assess 从练习池挑选对应的新题。没有合适题时显示缺口，不让 sidechat 临时生成一题再自行判掌握。

同一道题的提示、讲解和聊天内回答仍属于辅导。要形成独立证据，应换题、撤掉帮助，并保留帮助与题目见过的记录。候选误解重复出现不必反复派题；已被检查或用户纠正的候选仍保留来源，但显示后续结果。自动判断规则归 learner，题目独立性归 assess。

### 草稿、提交、评估和应用分开

侧边会话根据明确修改意图形成可读草稿：改什么、为什么、涉及哪个对象、当前版本是什么、资料依据和不确定处是什么。学习者点击“提交给主老师”才进入评估。报错批注自动形成提案的规则由 annotation 执行，两种入口不应混成“所有聊天建议自动提交”。

当前 Proposal 状态是 open/accepted/rejected/applied/withdrawn，没有 draft/submitted。推荐草稿先由 sidechat 或 annotation 保存，明确提交时调用 core.proposals 创建 open；只有需要统一跨单元草稿生命周期时才扩契约，不能暗改 open 的含义。

core 保存提案，tutor 解释处理意见，目标主人单元经服务执行。提交后教材或阶段已改动时，主老师重新核对版本；不把旧草稿直接覆盖新版。没有可确认目标时先澄清，不能用任意 targets 满足 schema。

当前 tutor 尚未形成完整的侧边提案消费链，不能仅有 proposalIds 或事件就验收“修改流程完成”。可先验收草稿、提交和待评估可见性，实际评估/应用列为 tutor 做深的依赖；不在本研究中插手 Curriculum 或实现主老师处理器。

### 主界面与跨课程范围

按已确认方向应支持主界面提问。推荐先明确选中的课程或全局知识对象，所有上下文标明来源；一次会话涉及多门课时按帮助对象分别归因，不默认给每门课记同一疑问，也不自动改多门课程。

当前 open 强制课程，notes 路径属于课程。无课程会话的笔记存放、提交提案归属和工作区需要 core/tutor 明确接口。推荐首批让主界面选择一门课后答疑；真正无课程或多课程会话在边界明确后实现。这只是分批建议，不取消已确认的跨课程能力。

### 界面与设置

入口仍保持直接输入首问，选中目标可预览原文和出处。已存在会话时切页不会自动替换其目标；用户可以明确把新的选区带入会话，作为有时间和版本的上下文消息。侧栏收起、当前回答结束、整次会话结束分别表达，关闭进度和失败重试放在原操作位置。

历史列表展示主题、课程、整理状态与原件入口；总结条目能回看原消息，纠正不覆盖旧记录。提案显示草稿、待评估和处理结果。帮助标签说明“这次使用了讲解，之后再独立验证”，不暗示扣分。测试操作模式和离开测试讨论的后果在输入区附近明确显示。

复用 kit Chat、共享控件和 shell 的面板、窄屏与主题规则，避免批注编辑器、原件阅读器和聊天分别抢占右栏。教学角色及总结模型继续由 roleModel 登记；确有使用需求的输入预算或开关由所属单元 Config 提供并动态生效，密钥仍用既有 secret 服务。后续界面实现再按 learning-ui-review 验收键盘、三宽度和双主题，并保留 Codex 调整部分的审美复核；本次不截图或改样式。
