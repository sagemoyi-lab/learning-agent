# 文档写法

把约定写够，再删掉推理过程、重复和装饰。这是指引，不是脚本。思路参考 DSH 的 `dsh-doc`、`dsh-prose-standard` 和 `dsh-trim-cot-leakage`（MIT），按本项目改写。

## 各文档管什么

每件事只有一个家。别处要提到时，写一句结论，再链接过去，不复制整段解释。

| 文档 | 管什么 | 不放什么 |
|---|---|---|
| `AGENTS.md` | 每次会话都要守的规则，每条一到三行，加链接；按需读什么 | 做法、例子、本机环境的细节（放 development.md 或技能） |
| `packages/AGENTS.md` | 改 `packages/` 下代码时的规则 | 根目录已有的规则 |
| `docs/PLAN.md` | 方向、设计原则、单元地图、技术底座、模型策略、开发路线；"现在"一节 | 单元的细节、做完了哪些的清单 |
| `docs/<单元>/design.md` | 这个单元现在怎么运作、为什么这样做 | 批次、已验收的验收标准、进度标注、变更经过 |
| `docs/<单元>/proposals/` | 进行中的功能：问题、方案、放弃的方案、验收标准、风险 | 做完的功能（并进设计文档后删掉提案） |
| `docs/<单元>/research.md` | 按日期分节的调研记录，设计这个单元时读 | 现状 |
| `docs/contracts.md` | 单元之间的总规则、数据归属、服务和事件、接口约定 | 类型的完整定义（在 `packages/contracts`）、单元内部的细节 |
| `docs/journey.md` | 跨单元的学习流程 | 单元内的细节 |
| `docs/development.md` | 本机构建、启动、验收、截图的做法 | 规则（放 AGENTS.md） |
| `docs/trial.md` | 写给用户的试用清单 | 给助手的说明 |
| `docs/throughts.md` | 用户原话：只追加，不改写，保留原有的写法和错字 | — |
| `docs/history/` | 冻结的旧记录：不再修改，也不作为现状的依据 | — |
| `README.md` | 怎么装、怎么启动、怎么用；每条命令都实际跑过 | 进度 |
| `.agents/skills/` | 某一类工作的做法和判断标准 | 产品事实 |
| 提交说明 | 做了什么、为什么、怎么验证的、结果 | — |
| 代码注释 | 代码表达不了的约定和原因 | 见下文 |

## 设计文档的结构

顶上一行链接代码、调研和契约，然后依次是：

1. **概要**：三到五句，写这个单元管什么、学习者能做什么、主要做法、最重要的边界。
2. **按功能分的小节**：每节写现在怎么运作。新功能并进它所属的小节，不在文末另起一节。
3. **数据与接口**：拥有哪些表和文件，提供哪些服务、接口和事件；细节链接到代码。
4. **关键决定**：每条写决定、理由、放弃的方案、来源和日期，例如"（10-16，你："……"）"。
5. **已知限制与以后再做**：现在做不到的、有意不做的、以后再做的。

## 提案怎样走完

1. 新功能开工前写 `docs/<单元>/proposals/<日期>-<主题>.md`，依次是 `## 问题`、`## 方案`、`## 放弃的方案`、`## 验收标准`、`## 风险`。跨单元的功能放在主要那个单元下，其他单元的设计文档链接过去。
2. 实现和验收期间，提案可以随时改。
3. 验收后：
   - 现在怎么运作，并进设计文档对应的小节；
   - 理由和放弃的方案，并进"关键决定"；
   - 发现的限制，写进"已知限制与以后再做"；
   - 验收做了什么、结果如何，写进提交说明；要用户试用的，写进 trial.md；
   - 删掉提案（git 里还有）。
4. 不做了的提案：如果以后可能再被提起，在"关键决定"里写一句为什么不做，然后删掉提案。

## PLAN 的"现在"

只写四件事：在做什么、在等用户什么（链接 trial.md）、下一步、审美复核点。一件事做完就删掉它那一句，不留"已完成"。

## 字数上限

`tests/docs.test.ts` 给这些文档设了上限：AGENTS.md、`packages/AGENTS.md`、PLAN 和它的"现在"、development.md、contracts.md、每份设计文档。超了时：

1. 先把不属于这里的内容挪到它的家，必要时留一句链接；
2. 再精简属于这里、但可以更短的内容；
3. 内容确实需要这些字时才调高上限，并在提交说明里写原因。

上限是护栏，不是删减目标。

## 保住完整的意思

删改一段话之前，先列出它包含的每个意思，逐个保住：

- 谁、做什么；
- 条件、时机、先后顺序；
- 必须、可以还是不得；
- 例外，以及"不会发生什么"的保证；
- 归谁负责、有什么副作用、失败了会怎样。

只删修饰、重复和叙述。字数少了不等于更好。

## 现状文档只写现状

AGENTS.md、README、PLAN、设计文档、契约、技能、代码注释，描述的是当前的代码。

- 不写变更经过：避免"原来、以前、改成、现在、这次、本轮、新增了"这类说法。
- 不写进度标注："已技术验收""待你试用""第一步已完成"会过时；要用户试用的写进 trial.md，没做的写进提案或"已知限制与以后再做"。
- 不引用读者看不到的东西：会话里说的"方案 B""第 3 条"、没提交的草稿。
- 变更经过放进提交说明。

检验方法：一个只看得到当前仓库的人，能不能找到每个引用、核实每个说法？不能，就改写成现状，或者删掉。

修好的问题，在注释里写成"没有 X 时会发生 Y"，不写"以前会 Y"。

## 只写验证过的操作

README、AGENTS.md、development.md、技能里的每条命令、配置、默认值和错误提示，都要在当前代码上实际跑过，或者查过代码。

- 跑不了的（缺密钥、要用付费服务），写明谁来验证，不凭记忆写。
- 复现不了的说法，要么删掉，要么改正；不要改测试去迁就文档。

## 代码注释

- 写代码表达不了的东西：约定、不变量、竞态顺序、归属、安全边界、出人意料的失败行为、不明显的原因。
- 不复述代码，不叙述控制流（"先……然后……"），不讲解测试的流程。
- 模块开头用一两句说清职责和依赖；复杂的原因链接到文档。
- 空的 `catch` 要写明为什么可以忽略。
- 注释用英文，和现有代码保持一致；文档和写给学习者看的文字用中文。

## 审查或精简的步骤

1. 明确范围（哪些文件）。没给范围就先问。
2. 先读权威来源（代码、测试、契约），再判断一段话对不对。
3. 逐段决定：保留、补充、精简、改写、挪到它的家，还是推迟。只在任务允许修改时才动手。
4. 先改"家"，再改引用它的地方。
5. 跑检查：
   - `pnpm vitest run tests/docs.test.ts tests/skills.test.ts`；
   - `git diff --check`；
   - 改了命令就重跑一遍。
6. 汇报：看了哪些文件、改了什么、有意保留了什么、推迟了什么。

## 校准例子

**保住每个意思**

- 原文："长的小节按小标题分成几部分写；某部分被截断就对半拆开重写；同一课时连续两次失败就交还学习者。"
- 删过头："教材分部分生成。"丢了截断后的处理和失败后交还这两件事。

**批次改成功能小节**

- 原文：设计文档里有"## B 批：测试按规则组"和"## C 批：拍照作答"，各带"### 验收标准"。
- 改后：拆进"摸底""阶段测试""作答与判分"这些功能小节，写现在怎么运作；验收标准删掉（结果在当时的提交说明里），仍然成立的限制写进"已知限制与以后再做"。

**进度标注删掉**

- 原文："**已完成，待你试用：**资料仓库和本课资料（10-12 试用反馈）。主界面的'资料库'是所有课程共用的仓库……"
- 改后："主界面的'资料库'是所有课程共用的仓库……"要试用的那一条写进 trial.md。

**变更经过改成现状**

- 原文："资料库现在改用云端解析了，原来是本机。"
- 改后："资料库的设置项 `parser` 为 `cloud` 时，PDF 上传到 MinerU 云端解析；为 `local` 时用本机 MinerU。"

**看不到的引用**

- 原文："按方案 B 的默认值。"
- 改后：直接写出默认值，或者链接到设计文档里写这个决定的那一条。

**修复写成"没有 X 会怎样"**

- 原文："以前教材会把习题写进去。"
- 改后："写教材时只给模型教学部分；资料里留着习题和答案时，模型会把习题写进教材。"

**删掉流程叙述**

- 原文：`// 先检查列表是否为空，为空就返回，否则继续`
- 改后：直接删掉。如果提前返回是为了保护某个不明显的约定，只写这个约定。

**适用范围的说明要留着**

技能里"这是指引，不是清单"这类话会改变助手使用技能的方式，不能当作废话删掉；删的是反复劝说的那几段。
